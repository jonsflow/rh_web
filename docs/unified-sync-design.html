Unified Sync Design

The unified app already serves three asset types from one set of routes. It still reads three databases. This is the layer that builds its own — the fetch and sync path, following what the three apps already do, so nothing new is invented and nothing is copied.

The rules this follows

01

Store what the API returns. The payload is kept verbatim on the row, as all three apps already do in their raw_data column. A parse mistake is then never destructive: re-derive rather than re-fetch.

02

The sync builds the database. Nothing reads the three original databases to fill the new one. There is no import and no migration — the unified database is populated the same way the other three were, by syncing.

03

Follow what the apps do. Parse on ingest with the raw kept beside it; positions rebuilt after insert where that is what the asset does today; the update endpoint as the trigger. No sync on boot, because none of the three does that.

04

Build nothing extra. No separate process, no raw-only table, no abstraction that a second asset would not have needed anyway.

05

The three apps stay the control. They keep running on their own databases and showing known-good figures, so a unified answer can be diffed against them. One copy of each parse feeds both, so they cannot drift apart.

The sync, as it works today

All three fetchers are the same four beats, written three times.

update_data(account)
  login_robinhood()            3 copies, identical
  fetch_<asset>_orders()        broker call — genuinely per-asset
    db.insert_orders(payloads) parse and INSERT welded in one loop
    db.rebuild_positions()     options and futures; stocks pairs at read
  get_processed_data()         read back

The only part that differs per asset is the broker call and the parse that follows it. Everything around them is the same work three times.

The shape

One pipeline. The parts that differ are the parts with three implementations.

sync(asset, account)
  login                                  shared
  since    = watermark(asset, account)    shared — max(created_at) in unified.db
  payloads = broker_call[asset](since)    per asset
  rows     = model[asset].from_payload()  per asset — the parse
  write(orders, rows)                     shared
  pair[asset]()                           per asset

The sync never branches on asset type. It looks up the model and calls the same two methods on it, so a fourth asset is a fourth model rather than a fourth code path.

A model per asset

models/ already holds OptionOrder, a dataclass mirroring the options schema, used by services/data_repository.py. The two new models follow it rather than introducing a pattern.

ModelMirrorsThe parse it owns
OptionOrder
exists		 option payload Multi-leg strike and type joined into one string; option ids from the leg URLs
StockOrder
new		 stock payload Flat fields, already normalized by its data fetcher
FuturesOrder
new		 futures payload Double-nested realizedPnl.amount; contract and side off the first leg; trade date converted to Eastern from the execution time

Each exposes the same two methods:

from_payload(payload, account)  classmethod — broker payload to model
to_row()                        model to unified column dict
The parse moves, it is not rewritten

The parsing code is lifted out of each insert_orders verbatim into from_payload, and insert_orders then calls it. One copy feeds both schemas. That is what keeps the three dashboards usable as the control, and it gives those parsers their first direct test coverage — today they are exercised only by a signature check at tests/test_accounts.py:162.

Pairing: each asset keeps what it does

Orders become positions three different ways. That is not duplication to collapse — the algorithms genuinely differ — so each asset keeps its own behavior and writes to the one positions table.

AssetHow it pairsWhereStored?
options Open and close orders matched on the option key portfolio/database.py:161 rebuilt after insert
futures Opening orders matched with closing ones per contract futures/database.py:218 rebuilt after insert
stocks FIFO, buys to sells, account in the grouping key stocks/database.py:139 derived on read

So the positions table holds options and futures rows, and stocks derives from unified orders when asked. No asset gains a step it does not have and none loses one.

The code plan

1

The models

StockOrder and FuturesOrder added beside OptionOrder; each gets from_payload and to_row, with the parse lifted out of the three insert_orders methods. Those methods then call their model, so the original apps keep writing exactly what they wrote before.

models/{option,stock,futures}_order.py · {portfolio,stocks,futures}/database.py

Verify A payload dict in, the expected row out, per asset — no database and no broker. The existing suite still passes, which is what says the three apps are writing what they wrote before.

2

The write and the watermark

insert_orders(asset_type, rows) on the unified database, ignoring an order it already has, and watermark(asset_type, account) for the incremental start date the fetchers already compute from get_last_order_date().

unified/database.py

Verify Rows constructed in the test land under canonical names; inserting the same order twice leaves one row; the watermark is per asset and per account, so selecting a second account does not re-fetch from the first one's date.

3

Pairing into the unified positions table

Options and futures rebuild positions from unified orders into unified columns. Stocks stays derive-on-read. The algorithms are the existing ones, reading and writing different column names.

unified/ · the three pairing implementations

Verify A small set of orders built in the test, run through the old pairing and the new one, asserting the same positions come out. Offline, no broker, no stored data.

4

The sync

Login, broker call, model, write, pair — per asset, behind one entry point, called from /api/<asset_type>/update as it is now.

unified/ · unified/unified_web.py:142

Verify The whole sync runs against a fake broker returning payloads, and rows land with asset type and account set. Nothing authenticates. The real populate is a live sync, run by you.

5

The app reads unified, the translation goes

unified/assets.py reads the unified database instead of the three files. One schema means nothing left to translate, so shared/field_config.py, the asset_fields block in config.json and the roughly thirty field names in asset-config.js all go.

unified/assets.py · shared/field_config.py · config.json · shared/static/js/asset-config.js

Verify Every unified figure diffed against the same figure from the standalone dashboard. Futures 2025-02-24 reads −19.14, the after-fees figure, and the four tests failing today pass.

Step 5 has a precondition

Steps 1 through 4 are all verifiable offline. Step 5 compares unified figures against the three dashboards, which needs the unified database to hold your data — so it waits on a live sync, which is yours to run. Until then those comparisons have nothing to compare and the four failing tests stay failing, which is expected rather than a regression.

Deliberately not built

No import from the three databases. No separate normalizing process. No raw-only table distinct from the parsed row, because the apps already keep both on one row. No sync on boot. No broker abstraction — the design doc's three rules already keep robin_stocks confined to the fetchers, and the models are where a second broker's names would be absorbed.
