Unified Sync Code Plan

The unified app becomes self-contained: its own models, services, database, frontend and sync. It imports nothing from the three standalone apps and nothing from shared/. Five steps, each one a commit.

Revised from rev 1

  • Nothing shared. The libraries the unified app needs are copied into unified/. shared/ stays where it is for the standalone apps and the risk manager; unified stops importing it.
  • The standalone apps are out of the equation. No to_asset_row, no second column-name set, no second repository. portfolio/, stocks/ and futures/ are not touched by any step.
  • Models and services in parity. Three order models with one interface, three services with one interface. No SQL in any service.
  • Stocks is materialized like the other two, now that it has a service returning positions.
  • The options service question is gone. It only existed because a service knew about storage. None of them will.

Step 2 · The database

2

The only SQL in the app

Schema and 12 tests exist. This adds the writing half, plus the two tables that come across from shared/.

Added to UnifiedDatabase

orders(asset_type, account)          -> List[dict]

Accounts and journals move in

The journals table is already in the schema. accounts is added, so accounts.db and journals.db stay with the standalone apps and unified reads neither. unified/accounts.py and unified/journals.py are the copied modules pointed at unified.db.

Why the watermark takes an account

get_last_order_date() is per database today, and one database is one asset, so it never needed an account. Here it does: without it, selecting a second account would start its first fetch from the first account's latest order and silently skip everything older.

Step 3 · The services

3

Three services, one interface, no storage

Orders in, positions out. A calculation can then be changed in one file without touching a query.

build_positions(orders: List[dict]) -> List[Position]

The same signature on all three. No SQL, no database handle, no file path — which is what makes each one testable on a list of dicts and replaceable on its own.

ServiceLifted fromWhat it does
option_service services/option_service.py
+ position_classifier
+ pnl_calculator		 Groups by option key, aggregates weighted prices, then classifies closed / expired / open and derives P&L. Already storage-free — it takes tuples and returns objects — so this is a copy with dict input and canonical field names
stock_service stocks/database.py
139–241		 FIFO buy queue per (account, symbol), partial fills splitting a buy across sells. Currently reads its own SQL; the query moves to the database and the algorithm arrives pure
futures_service futures/database.py
218–310		 Groups by (account, contract), averages open and close prices, sums the broker's realized P&L. Same treatment: the SQL stays behind, the algorithm comes across

Why options needs a service and the other two barely do

Futures P&L arrives from the broker per order, so pairing is bookkeeping. Stocks P&L is proceeds minus cost. Options P&L has to be inferred: a position can end by expiring with no closing order, direction flips the sign of every calculation, there is a ×100 contract multiplier, and a close whose open predates the fetch window has to be excluded or it reports a profit that never happened. The services are in parity so that each is easy to change; that does not make them equal in size.

Two existing behaviors carried across as-is

Spreads are skipped. process_raw_orders_to_positions does if is_spread_strategy(strategy): continue, so multi-leg orders never become positions — valuing one at expiry needs to know which strikes finished in the money, and that was never built. It is why 3,356 option orders produce 878 positions. Orphaned closes become status 'orphaned' with null P&L. Both come across unchanged; changing either is its own decision, not part of this.

Step 4 · The sync

4

The pipeline, and the step that makes unified.db exist

unified/sync.py

sync(asset_type, account=None, broker=None, db=None) -> dict
    since    = db.watermark(asset_type, account)
    payloads = broker.orders(asset_type, since, account)
    rows     = [MODELS[asset_type].from_payload(p, account).to_row()
                for p in payloads]
    written  = db.insert_orders(asset_type, rows)

    orders    = db.orders(asset_type, account)
    positions = SERVICES[asset_type].build_positions(orders)
    db.clear_positions(asset_type)
    paired    = db.insert_positions(asset_type, [p.to_row() for p in positions])

MODELS   = {'options': OptionOrder, 'stocks': StockOrder, 'futures': FuturesOrder}
SERVICES = {'options': option_service, 'stocks': stock_service,
            'futures': futures_service}

No asset-specific branch anywhere in it. Two lookups by asset type, and every asset takes the same path — including the rebuild, now that stocks has a service.
